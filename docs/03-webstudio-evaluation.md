# Webstudio evaluation

**Verdict: study it closely, adopt none of it, steal three of its ideas.** Webstudio is the most mature open-source project in this category and several of its design choices solve problems named in the solution definition. Its licence and its editing philosophy both rule it out as a foundation.

## What it is

An open-source visual builder positioned against Webflow: full CSS control, connects to any headless CMS, sites hostable anywhere. Around 8.9k stars, 1.6k forks, ~6,700 commits, active, with a public roadmap and a company behind it.

## Architecture

| Layer | How it works |
| --- | --- |
| Builder | Real-time collaborative, offline-first; Nanostores signals mixed with React, to update large trees without heavy memoisation |
| Data model | Project as a serialisable JSON tree of component instances; styles in a CSS Typed Object Model — fully typed JSON values, not strings |
| Styling | Design tokens aligned to the W3C spec; tokens, local styles and tag styles are all mixins merged in order, which removes CSS specificity conflicts |
| Sync | Changes travel as RFC 6902 JSON Patches, generated by Immer |
| Publishing | A CLI pulls project data, compiles it into components, scaffolds routes and CSS for the target framework, then deploys |
| Hosting | Cloudflare Workers, one isolated Worker per project, server-rendered; the compiled app can also be deployed elsewhere |
| SDK | Framework-agnostic core, plus React primitives and Remix / Next integrations; component metadata auto-generates prop types from TypeScript |

## Licence and business model

Open core. The builder core is AGPL-3.0-or-later — chosen deliberately as a copyleft licence rather than a source-available one, and they say so publicly. Features aimed at organisations, such as fine-grained permissions management, are proprietary and paid. Revenue comes from Webstudio Cloud and private-cloud offerings for agencies. No separate commercial licence for the core is advertised.

For a hosted SaaS this is the blocking fact: AGPL's network-use clause reaches software offered over a network, so building this platform's studio on the Webstudio core would put obligations on the combined work. Their own documentation adds a second obstacle — self-hosting the Builder in production is **not recommended**; the supported self-hosting path is exporting and hosting the *published sites*, not running the builder as a service.

## Where it matches the solution definition

| Solution definition | Webstudio |
| --- | --- |
| Design tokens, W3C DTCG format | Tokens aligned to the W3C spec, as first-class mixins |
| Templates as versioned packages | Framework-agnostic SDK with typed component metadata |
| Release-based publishing, instant rollback | Compile-then-deploy pipeline producing a deployable artifact per project |
| Control and data plane fail independently | Published sites run as isolated Workers, entirely separate from the builder |
| Per-block provenance and three-way merge | JSON Patch change stream over a JSON tree |

## Where it conflicts

| Conflict | Consequence |
| --- | --- |
| Full CSS control, Webflow-style | Contradicts Decision 1. Accessibility guarantees, responsive behaviour and central template fixes all depend on not offering this |
| AGPL core | A proprietary managed service cannot build on it without licence obligations |
| Builder not production-self-hostable | The one component worth adopting is the one they advise against running |
| Aimed at designers and developers | This platform's primary user is a non-technical owner who wants the site run for them |
| No managed-service layer | No tenancy control plane, billing, metering, audit engine, generation agent or service loop |
| Static export gaps | Static exports drop dynamic pages, redirects, status codes, webhook forms, image optimisation, robots.txt and sitemaps — several of which are non-negotiable for the SEO promise |

## Three ideas worth taking

1. **JSON Patch as the change stream.** This is the most valuable idea here and it lands directly on the hardest problem in the spec. Representing every edit as an RFC 6902 patch over a JSON content tree gives per-change attribution for free, makes the generated-versus-human-edited distinction a property of the patch log rather than a separate provenance system, and turns the three-way merge on template upgrade into a tractable operation over structured data instead of a merge over rendered markup.
2. **Styles as ordered mixins over a typed CSS object model.** Tokens, component styles and local overrides merged in order, with no specificity to reason about. This makes token-level contrast validation a computation rather than a scan, which is exactly what the accessibility requirement needs.
3. **Compile, then deploy an isolated artifact per site.** A concrete, working instance of the release model in this spec, including the per-tenant isolation argument for running each published site in its own worker.

## What to read in the repo

The styling and token packages first, for the mixin model. Then the patch and sync layer, for the change stream. Then the CLI and SDK boundary, to see where project data stops being data and becomes a deployable app — that boundary is the same one this platform has to draw between content and release.

Read it as architecture, not as a dependency. Nothing should be copied into the codebase.
